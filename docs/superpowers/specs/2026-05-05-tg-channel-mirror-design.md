# TG Channel Mirror — Design

**Дата:** 2026-05-05

## Цель

Зеркалить посты из ~10 публичных Telegram-каналов в один личный приватный канал-«ленту». Без фильтрации содержимого: всё, что появляется в источниках, появляется в ленте.

## Out of scope

- Фильтрация рекламы (LLM, правила, классификация) — обсуждалось, выкинуто.
- Поддержка приватных каналов (по invite-ссылке).
- Использование личного TG-аккаунта (юзербот через MTProto).
- UI / админ-панель / web-интерфейс.

## Архитектура

Один Python-процесс на Railway, без TG-сессий пользователя. Чтение через публичную веб-версию канала (`https://t.me/s/<username>`), публикация через Bot API.

```
┌────────────────────────┐         ┌──────────────────┐
│  t.me/s/<channel>      │ ──HTTP─▶│  Парсер (HTML)   │
│  (публичная веб-страница)│         └────────┬─────────┘
└────────────────────────┘                  │
                                            ▼
                                   ┌──────────────────┐
                                   │ SQLite (state)   │
                                   │  last_seen_id,   │
                                   │  text hashes     │
                                   └────────┬─────────┘
                                            │ (новые посты)
                                            ▼
                                   ┌──────────────────┐
                                   │  Bot API         │──▶ Личный канал
                                   │  sendMessage,    │
                                   │  sendPhoto,      │
                                   │  sendMediaGroup  │
                                   └──────────────────┘
```

## Стек

| Слой       | Технология                          |
|------------|--------------------------------------|
| Язык       | Python 3.12                         |
| HTTP       | `httpx` (async)                     |
| Парсинг    | `selectolax` (быстрый HTML-парсер) |
| Bot API    | `aiogram` 3.x                       |
| Состояние  | SQLite через `aiosqlite`            |
| Хостинг    | Railway (один long-running процесс) |

Никакого LLM, никакого Groq, никаких user-сессий.

## Поток данных

Полный цикл (повторяется каждые ~60 секунд):

1. Для каждого канала из конфигурации:
   1. `GET https://t.me/s/<username>` через `httpx`.
   2. Парсинг HTML: извлечь все посты с `data-post="<channel>/<id>"`.
   3. Отфильтровать посты с `id > last_seen_id[channel]` из SQLite.
   4. Для каждого нового поста:
      1. Извлечь: текст (с форматированием), медиа-URL'ы, ссылку на оригинал, `grouped_id` (для альбомов).
      2. Проверить дедупликацию: hash от первых 200 символов текста встречался ли в `seen_hashes` за последние 24 часа?
         - Если да → пропустить, лог в SQLite.
         - Если нет → продолжить.
      3. Сформировать сообщение: текст + строка-атрибуция `\n\n📡 @<channel>` (ссылка ведёт на оригинальный пост).
      4. Если длина текста > 4096 символов → разбить на два сообщения по границе абзаца.
      5. Отправить через Bot API:
         - Только текст → `sendMessage`.
         - Текст + одна картинка → `sendPhoto` с `caption`.
         - Текст + одно видео → `sendVideo` с `caption`.
         - Альбом (одинаковый `grouped_id`) → `sendMediaGroup`.
      6. Обновить `last_seen_id[channel]` и записать hash в `seen_hashes` в SQLite.
2. Спать 60 секунд, повторить.

## Поведение на первом запуске

Когда скрипт стартует впервые (пустая SQLite), он **не публикует существующие посты задним числом**. Вместо этого записывает текущий `last_message_id` каждого канала и начинает реагировать только на новые посты, появляющиеся после старта.

## Конфигурация (env vars)

| Переменная     | Назначение                                            |
|----------------|--------------------------------------------------------|
| `BOT_TOKEN`    | Токен бота из @BotFather                             |
| `CHANNEL_ID`   | ID или `@username` целевого канала                   |
| `CHANNELS`     | Список источников через запятую: `durov,telegram,...` |
| `POLL_INTERVAL`| Период опроса в секундах (default: 60)               |
| `DEDUP_WINDOW` | Окно дедупликации в часах (default: 24, `0` = выкл.) |

Имена каналов в `CHANNELS` — без `@`, как в URL `t.me/<имя>`.

## SQLite-схема

```sql
CREATE TABLE channel_state (
  channel TEXT PRIMARY KEY,
  last_seen_id INTEGER NOT NULL,
  updated_at TIMESTAMP NOT NULL
);

CREATE TABLE seen_hashes (
  hash TEXT PRIMARY KEY,
  first_channel TEXT NOT NULL,
  first_seen_at TIMESTAMP NOT NULL
);
CREATE INDEX idx_seen_hashes_time ON seen_hashes(first_seen_at);
```

Старые записи `seen_hashes` (старше `DEDUP_WINDOW` часов) очищаются раз в час фоновой задачей.

## Edge cases

- **Канал не существует / стал приватным** → лог ошибки, продолжаем с остальными.
- **`t.me/s/<channel>` отдаёт 404 или таймаут** → лог, ретрай в следующем цикле.
- **Bot API rate limit** (30 msg/sec на бота, 20 msg/min в один канал) → exponential backoff на `429`.
- **Удалённые посты в источнике** → не наша забота, мы их не увидим.
- **Закреплённые посты** → парсятся как обычные. На первом запуске игнорируются (не превосходят свежий `last_message_id`).
- **Видео-кружки и голосовые** → отправляются как `sendVideoNote` / `sendVoice` через прямые URL.
- **Опросы (polls)** → Bot API не позволяет переслать опрос как опрос без user-session; шлём текст «📊 [опрос] <вопрос>» + ссылка на оригинал.
- **Платный/премиум-контент** → не парсится в `t.me/s/`, пропускаем.

## Что от пользователя руками (один раз)

1. ✅ Создать приватный канал «Лента».
2. ✅ Создать бота через @BotFather, получить токен.
3. ✅ Добавить бота в канал админом (право Post messages).
4. Зарегистрироваться на Railway, подключить GitHub-репо.
5. Залить env vars в Railway: `BOT_TOKEN`, `CHANNEL_ID`, `CHANNELS`.

## Тестирование

- Юнит-тесты для парсера на сохранённых HTML-фикстурах (несколько типов постов: текст, фото, альбом, видео, опрос, длинный пост).
- Юнит-тесты для дедупликации (hash + временное окно).
- Юнит-тесты для длинных постов (разбиение на части).
- Интеграционный тест: реальный `httpx` против `t.me/s/telegram` (официального канала Telegram), проверка что парсер возвращает >0 постов с ожидаемой структурой.
- Smoke-тест публикации в тестовый канал перед деплоем.
